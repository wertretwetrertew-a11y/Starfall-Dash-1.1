# Starfall Dash — безопасная перестройка репозитория

Дата подготовки: 2026-09-29

## 1. Зафиксированная исходная точка

Текущая рабочая версия сохранена без изменений в ветке:

- `backup/pre-restructure-2026-09-29`
- исходный commit: `4f10ab5562ba05e3bfb02210861a610fd6fc2be9`

Отдельная рабочая ветка для перестройки:

- `refactor/preparation-2026-09-29`

На момент подготовки backup и рабочая ветка идентичны.

## 2. Главный принцип

Не переписывать игру целиком и не менять игровой баланс/визуал одновременно с архитектурой.

Каждый этап должен:
1. иметь одну понятную цель;
2. сохранять существующее поведение;
3. проходить проверку ссылок/импортов;
4. быть отдельным commit;
5. при проблеме откатываться на предыдущий commit или backup-ветку.

## 3. Что сейчас нельзя делать первым

Не начинать с разрезания `js/gameplay.js` на десятки файлов.

Сейчас скрипты используют общие глобальные переменные и зависят от порядка подключения:

1. `js/balance-config.js`
2. `js/core-data.js`
3. `js/meta-ui.js`
4. `js/gameplay.js`
5. `js/roguelike-v3.js`
6. `js/rogue-planets.js`
7. `js/menu-motion.js`

Без карты зависимостей такое разделение может сломать игру.

## 4. Безопасные этапы

### Этап A — инфраструктура
Только подготовка структуры:
- `src/`
- `assets/`
- `tests/`
- `docs/`
- `tools/` в отдельной зоне
- `.gitignore`
- минимальная конфигурация Vercel при необходимости

Игровая логика на этом этапе не меняется.

### Этап B — данные
Отделить баланс и статические игровые данные от логики:
- balance
- abilities
- upgrades
- enemies
- heroes/classes
- stages

Особенно важно для будущего Bot Lab: редактор баланса должен работать с данными, а не с огромным файлом игровой логики.

### Этап C — режимы
Отделить Survival и Roguelike так, чтобы изменение Roguelike не затрагивало Survival.

Критическое правило для теста:
- Survival = ровно 1 жизнь независимо от Core.

### Этап D — UI
Разделить модальные экраны и UI по ответственности:
- menu
- mode select
- hero select
- profile
- shop
- cases
- core
- settings
- how-to-play
- death screen
- HUD

При этом внешний вид и расположение элементов не менять без отдельной задачи.

### Этап E — игровой цикл
Только после предыдущих этапов осторожно выделять:
- game state
- input
- collision
- update loop
- rendering
- enemy manager
- player logic

### Этап F — тесты
Добавить проверки критических правил:
- 1 жизнь Survival;
- получение XP/уровня;
- выпадение 3 осколков ядра на первом этапе;
- переходы этапов;
- урон при столкновении;
- способности персонажей;
- боссы только в Roguelike;
- сохранения;
- награды/баланс.

### Этап G — Vercel
После каждого крупного архитектурного этапа проверять:
- загрузку `index.html`;
- пути CSS/JS/assets;
- отсутствие 404;
- отсутствие JS-ошибок;
- работу Bot Lab отдельно от игры.

## 5. Что сохраняем неизменным

До отдельного согласования не менять:
- игровой баланс;
- существующие способности;
- правила режимов;
- внешний вид меню;
- позиции иконок;
- размеры игровых объектов;
- существующие изображения/аудио;
- поведение сохранений;
- Bot Lab и его launcher-файлы.

Архитектурная перестройка должна быть именно перестройкой, а не скрытым геймдизайн-обновлением.

## 6. Целевая структура

Целевая структура будет вводиться постепенно, а не одним огромным переносом:

```
src/
  core/
  player/
  enemies/
  modes/
  roguelike/
  systems/
  ui/
  rendering/
  audio/
  data/
  utils/

assets/
  images/
  audio/
  fonts/
  icons/

tools/
  balance-editor/
  debug/
  development/

tests/
docs/
```

## 7. Правило отката

Если после отдельного этапа появляются:
- белый/пустой экран;
- двойной интерфейс;
- пропавшее меню;
- ошибки загрузки;
- сломанный death flow;
- сломанный Roguelike;
- сломанный Survival;
- проблемы с Bot Lab;

этап не продолжать. Сначала вернуть предыдущий рабочий commit и найти причину.

## 8. Важное решение по main

Ветка `main` не должна изменяться до тех пор, пока отдельный этап перестройки не проверен.

Работа ведётся в `refactor/preparation-2026-09-29`, затем отдельные готовые этапы можно переносить в `main`.

## 9. Следующий шаг

Перед первым переносом нужно составить карту:
- какие функции относятся к какой системе;
- какие глобальные переменные используются несколькими файлами;
- какие функции вызываются из других файлов;
- какие DOM-элементы используются каждым модулем;
- какие данные читаются/изменяются Bot Lab;
- какие файлы являются чисто разработческими и не должны попадать в публичную часть игры.

Только после этой карты начинается реальное перемещение кода.
